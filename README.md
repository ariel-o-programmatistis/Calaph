Calaph is a mathematical symbolic encoding system designed to represent numerical and textual information through a formally defined set of primitive symbols, arithmetic operators, compositional rules, decimal notation, and sequential character mappings. The system is language-independent: Calaph defines the representation and grammar, while C and Bash provide implementations of that specification. A Calaph implementation is therefore responsible for converting external data into valid Calaph expressions, validating and evaluating those expressions, and reconstructing the original data during decoding. The objective of the system is to provide a deterministic, composable, and extensible symbolic representation in which complex numerical values can be generated from a small primitive vocabulary instead of assigning an independent symbol to every possible value.

The fundamental numerical alphabet of Calaph consists of three primitive representations. The symbol . has the numerical value 1, , has the numerical value 3, and <> represents 0. The initial numerical domain is constructed from these primitives according to the established representation rules: . represents 1, ., represents 2, , represents 3, ,. represents 4, .,, represents 5, ,, represents 6, ,,. represents 7, .,,, represents 8, ,,, represents 9, and ,,,. represents 10. These values form the basic vocabulary from which larger numerical expressions can be constructed. Calaph does not require a unique primitive token for every integer; instead, values outside the primitive range are generated through arithmetic composition. This makes the numerical representation potentially unbounded as long as the implementation supports the required numerical range.

The current arithmetic grammar defines two primary operations. A whitespace separator represents addition, while the apostrophe character ' represents multiplication. Consequently, an expression composed of multiple blocks separated by spaces is evaluated as the sum of those blocks, while a block containing ' represents a product. For example, ,', consists of two numerical operands, each representing 3, and therefore evaluates to 3 × 3 = 9. A sequence such as . , . evaluates as 1 + 3 + 1 = 5. Multiplication is intentionally restricted to a single operator per product: A'B is a valid multiplication expression, whereas A'B'C is not valid under the current grammar. The restriction provides a predictable parsing model and prevents the multiplication syntax from becoming ambiguous or requiring an additional precedence model. An implementation should therefore validate multiplication expressions before evaluation and reject expressions containing multiple multiplication operators within the same product.

An important property of Calaph is that numerical values and their representations are distinct concepts. Multiple syntactically different expressions can evaluate to the same numerical value. For example, ., represents 2, while . . also evaluates to 2 through 1 + 1. Likewise, values can be constructed through combinations of primitive composition, addition, and multiplication. This property means that a Calaph encoder does not necessarily have to use a single universal representation for every number. A basic implementation can use predefined representations for common values, while an advanced implementation can generate expressions dynamically and select representations according to an optimization criterion such as minimum character count, minimum operator count, or computational complexity. Canonicalization is therefore an implementation-level concern that can be defined independently from the fundamental mathematical semantics of Calaph.

Decimal numbers extend the same numerical model through structural delimiters. The symbol | separates the integer portion of a number from its fractional portion, while \ separates individual decimal digits. For example, ,|.\,. represents 3.14, where , evaluates to 3, . evaluates to 1, and ,. evaluates to 4. The representation of zero remains <>. An implementation must consequently treat | and \ as lexical elements of the decimal grammar rather than as arithmetic operators. Decimal parsing should distinguish the integer expression from the fractional sequence and reconstruct the resulting value according to the defined positional decimal semantics.

The textual representation of Calaph is implemented as a layer above the numerical system. Each supported character is assigned a numerical identifier, and that identifier is subsequently encoded using the Calaph numerical grammar. The current unified character mapping assigns numerical identifiers 1–27 to the Latin alphabet, including Ñ, 28–51 to the Greek alphabet, and 52–84 to the Russian Cyrillic alphabet. The Latin alphabet therefore occupies the first range, the Greek alphabet continues immediately after it, and the Cyrillic alphabet continues after the Greek range. The resulting mapping creates a single numerical namespace for multiple writing systems rather than maintaining independent numerical spaces for each alphabet. Encoding a character consequently consists of an alphabet lookup followed by numerical expression generation, while decoding consists of numerical evaluation followed by a reverse lookup. The architecture can be extended by allocating additional numerical ranges to other alphabets without modifying the fundamental arithmetic engine.

For textual serialization, the implementation must also distinguish character boundaries from the internal mathematical syntax of each numerical expression. The current implementation uses additional delimiters for this purpose, allowing individual encoded characters and words to be separated while preserving the meaning of spaces within numerical expressions. These serialization delimiters should be treated as part of the textual transport format rather than as fundamental mathematical primitives. A future formal specification can define these delimiters more strictly through a grammar or grammar notation such as EBNF, allowing independent implementations to guarantee interoperability at the lexical and syntactic levels.

The C implementation operates as a compiled Calaph engine. Its primary responsibility is to implement the Calaph specification using explicit data structures, numerical operations, string buffers, character mappings, lexical analysis, parsing, evaluation, and serialization. A typical encoding pipeline begins with an input buffer containing text. The implementation iterates through the input, normalizes or identifies each character, searches the unified alphabet table, obtains the corresponding numerical identifier, converts that identifier into a Calaph numerical expression, and appends the result to an output buffer. Decoding reverses the procedure: the input buffer is tokenized into serialized character representations, each numerical expression is parsed, its operators and operands are validated, the expression is evaluated, and the resulting numerical identifier is mapped back to a character. Functions such as encode_number(), decode_number(), encode_character(), decode_character(), encode_text(), and decode_text() can be used to isolate these responsibilities and maintain a modular implementation.

C provides direct control over the internal representation of the encoder and decoder. Numerical values can be stored in integer types appropriate to the supported range, expressions can be constructed in dynamically allocated or statically managed buffers, and the parser can operate directly over character arrays. This makes C particularly suitable for implementing a strict Calaph grammar because lexical analysis and syntax validation can be performed without relying on external interpreters. The program can distinguish invalid symbols, malformed multiplication expressions, invalid decimal separators, incomplete character tokens, numerical overflow, and unsupported character identifiers before attempting evaluation. A production-oriented implementation should therefore separate lexical validation from semantic evaluation so that malformed input cannot accidentally be interpreted as a different valid expression.

The Bash implementation implements the same mathematical and textual semantics using shell-native data structures and command-line facilities. Bash is fundamentally string-oriented, so Calaph expressions are naturally represented as shell strings and manipulated through parameter expansion, arrays, loops, conditional expressions, and functions. The encoder reads textual input, resolves characters against the alphabet mapping, constructs the corresponding Calaph expression, and writes the serialized representation to standard output. The decoder performs tokenization and numerical evaluation using Bash arithmetic and string-processing mechanisms. The program can expose Calaph as an interactive terminal application or as a command-line utility capable of receiving data through standard input and sending encoded data through standard output. This makes the Bash implementation particularly suitable for Linux pipelines, shell scripts, automation, file transformations, and rapid experimentation with the Calaph grammar.

The fundamental difference between the C and Bash implementations is therefore not the Calaph algorithm itself but the execution environment. C provides compiled native execution, explicit memory and data management, strong control over numerical operations, and a more suitable environment for developing a formal parser and larger implementation. Bash provides direct integration with the Unix shell, simple deployment as a script, convenient text manipulation, and interoperability with standard Linux utilities. Both implementations should nevertheless conform to the same external specification. If the C implementation generates a valid Calaph expression, the Bash implementation should be able to parse that expression and produce the same numerical result, provided that both implementations implement the same grammar and character mapping. This interoperability is essential if Calaph is to function as a genuine representation format rather than as a format tied to one particular application.

From an implementation perspective, Calaph can be modeled as a small domain-specific language processor. The lexical layer identifies primitive symbols and operators; the syntactic layer determines whether their arrangement conforms to the grammar; the semantic layer evaluates valid mathematical expressions; the character-mapping layer converts between numerical identifiers and characters; and the serialization layer converts internal representations into the external textual format. Encoding therefore follows the general transformation input data → lexical characters → character identifiers → numerical expressions → serialized Calaph, while decoding performs serialized Calaph → lexical tokens → numerical expressions → evaluated numerical values → character identifiers → reconstructed data. Keeping these layers independent allows the numerical engine to be reused independently from the text encoder, and allows the text layer to be expanded without rewriting the arithmetic evaluator.

Calaph should not be classified as encryption or cryptography in its current form. It is an encoding and representation system. Its representations are intended to be reversible through knowledge of the grammar and character mapping, but they do not provide cryptographic secrecy. Anyone possessing the specification can implement a decoder. If cryptographic protection is introduced in the future, it should be treated as an independent processing layer rather than being confused with Calaph's mathematical representation mechanism.

The long-term implementation of Calaph can therefore evolve toward a formally specified, language-independent standard. The mathematical grammar can be expressed using a formal notation, the lexical tokens can be explicitly defined, canonical representation rules can determine how encoders choose between equivalent expressions, numerical limits can be specified, Unicode normalization can be standardized, and the serialization format can be documented independently from the implementation language. C can then serve as a native reference implementation, while Bash can provide a lightweight Linux implementation and testing environment. Additional implementations can subsequently target other languages without modifying the underlying specification.

At its core, Calaph defines a transformation between information and mathematical symbolic structure. C and Bash do not constitute different versions of Calaph; they are different software implementations of the same Calaph language. The specification determines the meaning of ., ,, <>, ', whitespace, |, \, numerical composition, arithmetic evaluation, and character mapping, while the implementation determines how those rules are represented in memory, parsed, validated, evaluated, and exposed to the user. Calaph is therefore best characterized technically as a composable mathematical symbolic encoding system and domain-specific representation language, with a numerical core, an arithmetic grammar, a character-mapping layer, and a serialization mechanism designed to permit deterministic encoding, decoding, validation, and interoperability across independent implementations.
